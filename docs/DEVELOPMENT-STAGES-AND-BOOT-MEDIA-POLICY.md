# 开发阶段与启动介质原则（项目长期决策）

> 决策状态：已确认；适用于后续所有对话、源码审计、构建和实机验证。  
> 确认日期：2026-11-21

## 1. 核心原则

**当前 eMMC 绝对只读，是研究/测试阶段的临时安全约束；最终正式交付系统必须安装并运行在 eMMC 上，从 eMMC 启动。**

TF 卡只承担当前阶段的临时启动、隔离验证和必要的救援用途，不是最终产品的正式启动介质。不得把“TF 启动且 eMMC 永久只读”误写成最终架构目标。

## 2. 阶段 A：当前研究与验证阶段

当前阶段使用独立 TF 卡作为实验载体，保护 Panther X2 原有 eMMC 系统、数据和厂商数据。

- eMMC 必须保持绝对只读：任何启动组件、驱动、初始化脚本、用户空间服务、异常恢复分支、自动更新逻辑均不得向 eMMC 写入。
- 该约束覆盖正常路径和异常路径；不能只证明正常启动时没有写入。
- 需要审查 SPL/U-Boot、BL31/其他固件、内核、initramfs、根文件系统服务及更新工具可能触发的 eMMC 写入路径。
- 可以在源码、配置和 CI 中进行只读审计及纯构建验证；未经明确授权，不安装软件、不修改设备系统/配置/内核/驱动/网络服务，不写 TF、不写 eMMC、不启动实机测试。
- 当前测试中的 A/B 元数据、环境变量保存、Vendor Storage 初始化/写回、Fastboot/DFU/刷写等行为，凡可能触及 eMMC 的，均须在测试配置或执行路径中禁止，并验证禁止措施有效。
- “eMMC 零写入”是本阶段的安全验收条件，不是永久产品功能要求。

## 3. 阶段 B：最终正式交付阶段

正式版本的目标介质和启动路径明确为 **eMMC 安装、eMMC 启动、eMMC 运行**。

- 正式部署时允许向 eMMC 进行设计明确、受控且可恢复的写入，包括分区/文件系统建立、系统安装、配置持久化、升级和必要的启动状态记录。
- 可以评估并采用 A/B 启动、持久化 U-Boot 环境、更新/恢复机制、Vendor Storage 维护等能力；是否采用应由可靠性、安全性和维护成本决定。
- 任何写入仍必须有明确目标分区/区域、写入主体、触发条件、校验、掉电保护/失败处理及恢复方案。
- 必须保护板级身份数据和厂商保留区域（包括 Vendor Storage、MAC 等）。系统安装/升级不得无意覆盖或初始化这些区域；如确需维护，必须作为独立、受控操作设计。
- 最终交付必须提供分区布局、安装流程、升级与回滚、备份、救援启动和恢复方案。TF 可保留为救援介质，但不替代 eMMC 正式启动。

## 4. 组件选型与审计规则

不能因为某个 SPL/U-Boot/启动组件具备 eMMC 写入能力，就直接将其从最终候选中淘汰。

每个候选组件必须分别回答：

1. **正式架构适用性：** 能否可靠支持 Panther X2/RK3566 的 eMMC 启动、分区识别、启动顺序和板级初始化？
2. **测试阶段隔离性：** 能否通过编译配置、运行配置或明确的启动路径约束，在 TF 测试时确保不写 eMMC？
3. **正式写入可控性：** 在 eMMC 正式运行时，写入入口是否明确、可审计、可限制并具备失败恢复能力？
4. **数据保护：** 是否可能误写用户数据、Vendor Storage、启动固件或其他保留区域？

因此，当前 eMMC 只读审计的作用是保护实验环境、验证阶段隔离能力，而不是要求最终组件永久失去 eMMC 写入功能。若某个组件无法在当前测试阶段可靠隔离 eMMC 写入，应暂缓用于当前测试；这不自动等于它不适合最终 eMMC 产品。

## 5. 研究记录必须标明阶段

所有报告、构建计划和测试结论必须区分：

- **当前阶段约束：** TF 临时测试；eMMC 绝对只读；未经授权不写卡、不操作实机。
- **最终产品目标：** 正式系统安装于 eMMC，并从 eMMC 启动和运行；允许受控写入。
- **状态标签：** 已验证、静态审计确认、待验证、推测/候选。不得把设计目标写成已实现或已验证事实。

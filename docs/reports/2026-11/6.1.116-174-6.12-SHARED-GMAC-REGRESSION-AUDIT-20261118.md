# Panther X2 6.1.116 → 6.1.174 → 6.12 共享 GMAC 回归线索审计（2026-11-18）

## 1. 本轮目的

依据已归档的 6.12 Ethernet 软件审计结论，回溯新的可靠版本边界：

- 6.1.116：已验证正常；
- 6.1.174-rk35xx-ophub：最早有明确历史实机异常证据；
- 6.12.81-rk35xx-ophub：当前异常。

本轮不重新执行实机测试，只比较源码并寻找同时存在于 6.1.174 与 6.12、而 6.1.116 正常线没有的 GMAC/PHY 初始化差异。

## 2. 重要版本身份

Ophub 的 RK35xx 发布仓库说明明确将无 `flippy` 后缀的资产描述为在线自动编译的 RK35xx BSP 内核；发布资产中同时存在：

- `6.1.174.tar.gz`
- `6.12.81.tar.gz`

其工作流默认 kernel source 为 `ophub/linux-6.1.y-rockchip` / `ophub/linux-6.12.y-rockchip`，默认签名分别生成 `-rk35xx-ophub`。

2026-11-10 的 RK35xx 6.1 构建对应工作流使用的 Rockchip 6.1 源码树在当时已到 commit：

`c2f148dece4b67ebd30aefad1bdd1990f41e5633`

该 commit 与 `unifreq/linux-6.1.y-rockchip` 同步，提交时间为 2026-11-10。

> 限制：GitHub 公共 API 当前不能直接读取该 workflow job 的完整日志，因此本报告将 `c2f148...` 记为 6.1.174 构建源码的高置信度候选，而不把它写成已取得 job log 的绝对证明。

## 3. 发现：6.1.116 有一组 JL2xx1 专用 workaround，而 6.1.174 / 6.12 均没有

### 3.1 6.1.116 的 DMA reset 前 1500 ms 延时

6.1.116 实际工作源码：

`unifreq/linux-6.1.y@5eb841b59d6ead6e264163785a634e78f0253c8e`

`drivers/net/ethernet/stmicro/stmmac/stmmac_main.c` 的 `stmmac_init_dma_engine()` 在 DMA reset 前明确执行：

`msleep(1500);`

源码历史显示该改动来自 commit：

`49b5f340f346cc9a5b777499fce46150b691b70e`

标题：

`drv: net: ethernet: stmmac fix for jl2xx1 phy`

其父提交为：

`22e67a04d5f9912c7eaeb4603894ea2a4c3ffe36`

该 commit 的补丁明确加入：

`msleep(1500);`

并同时修改 `stmmac_mdio.c`。

### 3.2 6.1.116 的 MDIO 四次初始化写入

同一个 6.1.116 commit 在 `stmmac_mdio_register()` 注册 MDIO 总线后增加：

```
stmmac_mdio_write(new_bus,0,31,2627);
stmmac_mdio_write(new_bus,0,25,0x1801);
stmmac_mdio_write(new_bus,0,31,0);
stmmac_mdio_write(new_bus,0,0,0x8000);
```

即：

1. PHY 地址 0；
2. 切换到 vendor page 2627；
3. 写寄存器 25 = 0x1801；
4. 回到 page 0；
5. 写 BMCR = 0x8000 触发 PHY soft reset。

该 workaround 的 commit 标题明确指向 JL2xx1 PHY。

### 3.3 6.1.174-rk35xx：两项均不存在

在实际 6.1.174 RK35xx 源码候选：

`ophub/linux-6.1.y-rockchip@c2f148dece4b67ebd30aefad1bdd1990f41e5633`

检查结果：

- `stmmac_main.c` 的 `stmmac_init_dma_engine()` 没有 `msleep(1500)`；
- `stmmac_mdio.c` 的 `stmmac_mdio_register()` 没有上述四次 PHY 地址 0 写入；
- 该 Rockchip 6.1 分支的文件历史也没有发现该 JL2xx1 workaround 被重新加入。

### 3.4 6.12.81：同样不存在

实际审计的：

`ophub/linux-6.12.y-rockchip@661b2d8bf1284556f8876d5ed5fb80c64b22f94c`

同样：

- `stmmac_init_dma_engine()` 无 1500 ms DMA-reset 前等待；
- `stmmac_mdio_register()` 无上述四次 PHY 地址 0 写入。

因此形成了一条非常值得继续验证的共同线：

```
6.1.116 正常
  └─ JL2xx1 workaround 存在
       ├─ DMA reset 前 1500 ms
       └─ MDIO addr0 四次初始化写入

6.1.174-rk35xx 异常
  └─ 两项均不存在

6.12.81-rk35xx 异常
  └─ 两项均不存在
```

## 4. 这不是“已经证明根因”

目前不能直接说 Panther X2 的 RTL8211F 就一定需要这个 JL2xx1 workaround。

原因：

- workaround 的 commit 标题明确针对 JL2xx1；
- Panther 当前 PHY 已确认是 RTL8211F；
- 6.1.116 对 RTL8211F 工作正常，而该 workaround 在 116 中是全局 stmmac 路径代码，因此它确实会在 Panther 的工作环境中执行；
- 但目前没有证据证明那四次 PHY 写入对 RTL8211F 是必要的，或者 1500 ms 对 Panther GMAC DMA reset 是必要的。

因此当前正确状态是：

> **高价值候选回归项，尚未证明为根因。**

它比此前的“5 ms→100–200 µs GMAC clock delay”更值得优先研究，因为它同时满足三个条件：

1. 存在于已知正常 6.1.116；
2. 在首个明确异常 6.1.174-rk35xx 已消失；
3. 在当前 6.12.81 仍然缺失。

## 5. 另一个共享差异：RGMII delay 写入顺序

6.1.116 的 RK3568 GMAC 路径：

1. 先写 GMAC1_CON0：TX/RX delay value；
2. 再写 GMAC1_CON1：RGMII mode + delay enable。

6.1.174-rk35xx 和 6.12.81：

1. 先写 GMAC1_CON1：RGMII mode + DELAY_ENABLE；
2. 再写 GMAC1_CON0：DELAY_VALUE。

6.12 与 6.1.174 的 `rk3568_set_to_rgmii()` 实现已确认完全一致。

公开 Linux Rockchip patch 对这一变化有明确说明：该上游改动的目的，是让 RK3566/RK3568 在 RGMII_ID/RXID/TXID 模式下正确 enable/disable delay，并将 enable/disable 操作重新排序到 delay value 写入之前，以匹配其他 GMAC 和 vendor kernel。该 patch 不能证明 Panther RGMII 模式下的顺序改变就是本故障原因。

因此这条线保留，但优先级低于 JL2xx1 workaround。

## 6. 当前软件回归优先级

### 第一优先级

**JL2xx1 workaround 是否恰好是 Panther 6.1.116 正常、6.1.174/6.12 异常之间真正有区分度的差异。**

需要继续做纯源码审计：

1. 找出该 workaround 在原始 `unifreq/linux-6.1.y` 中的引入背景；
2. 检查它是否后来被删除、反向移植或有后续修正版；
3. 检查 RK35xx vendor 6.1 / 6.12 是否有 Rockchip 自己的等价实现；
4. 分析四次 MDIO 写入对 RTL8211F 的实际语义，尤其是 page 2627 / reg25 / BMCR reset；
5. 分析 1500 ms 等待与 Panther GMAC/RTL8211F reset、DMA reset 的时序关系。

### 第二优先级

继续保留 RGMII delay 写入顺序差异，暂不做实机验证。

### 已降级/关闭的方向

根据已有仓库报告，不重复：

- U-Boot 本体；
- CRU clock topology；
- clock_summary；
- pinctrl/phandle；
- PHY reset GPIO 本身；
- DMA descriptor/OWN/tail pointer；
- DWMAC4.20a ops；
- TX checksum/feature path；
- MTL queue / DMA channel 基本映射；
- Vendor Storage/MAC fallback；
- 普通 RX dropped 静态分析；
- 硬件波形测量。

## 7. 当前结论

这是目前为止第一次出现一个非常干净的版本分界候选：

> **6.1.116 正常环境包含一个后来在 RK35xx 6.1.174 和 6.12 BSP 中都不存在的 stmmac PHY/DMA workaround。**

它不能直接证明故障原因，但它比单纯的 clock delay 差异具有更强的历史回归解释力。

下一步不需要重跑任何已有实机测试，继续做 **JL2xx1 workaround 的源码/PHY 寄存器语义审计**。只有把它的作用解释清楚后，才决定是否值得设计一个最小单变量实机验证。

# RK3566 开发板 IPv4 DHCP 故障排查报告（脱敏版）

> 本文档由串口交互与第三方抓包实测记录整理而成，所有登录凭据、主机名、MAC 地址、IP 地址、本地路径等可识别信息均已脱敏。

---

## 1. 问题概述

- **设备**：RK3566 板卡（Panther X2），经 USB-CH340 转串口接入调试主机。
- **现象**：某一软件版本下 `eth0` 无法通过 DHCP 获取 IPv4 地址；换用另一软件版本后完全正常、可拿到固定 IP。
- **目标**：定位"换版本就好"的真正原因，而非停留在"发不出包"的表象。

---

## 2. 测试环境（脱敏）

| 项目 | 故障版本 | 正常版本 |
|---|---|---|
| 操作系统 | Armbian 26.11.0 noble | Armbian-unofficial 26.11.0 Jammy |
| 内核 | 6.12.81-rk35xx-ophub | 6.1.116-ophub |
| 板卡 MAC | `<MAC_A>`（本地管理/随机生成） | `<MAC_B>`（在路由器上静态绑定 `<静态IP>`） |
| IPv4 结果 | 无地址（仅 link-local IPv6） | `<静态IP>` |

- **串口**：CH340 USB-UART，`1500000` 8N1、无流控（115200 下读不到数据）；以 root shell 登录，登录凭据已脱敏。
- **调试主机**：双网卡（无线 + 有线），与板卡同网段；有线口地址 `<本机有线IP>`。
- **抓取工具**：板卡侧 `tcpdump`；调试主机侧 Python UDP/67 应用层监听器（第三方视角）。
- **路由器**：`<网关IP>`；经用户确认**无任何 MAC 过滤/限制**，唯一特殊配置是把 `<MAC_B>` 静态绑定到 `<静态IP>`，其他终端动态获取均正常。

---

## 3. 测试过程

### 阶段 1｜基础连通性确认
- 串口收发正常；`uname -r`、`ip -br link`、`hostname -I` 等命令均可执行。
- `ethtool`：1000M 全双工、Link up；IPv6 SLAAC 正常（多个全局地址 + 默认路由），IPv4 缺失。
- 无 IPv4 时 `ping <网关IP>` 报 `Network is unreachable`，属预期。

### 阶段 2｜板卡侧报文级检查
- `tcpdump` 抓到 DHCP Discover 并逐字节解析：`op/htype/hlen/flags/xid/chaddr/magic cookie` 全部合规。
- 选项 `53(Discover)`、`61(Client-ID)`、`55(PRL 17项)`、`57(576)`、`12(hostname)`、`255(END)` 均标准 —— **报文本身无畸形**。
- 服务器 `<网关IP>` 对板卡 Discover **零回应**；同一抓包中却给其他终端正常回 ACK（xid 不匹配）。地址池未满。

### 阶段 3｜排除客户端与报文变量
| 变量 | 操作 | 结果 |
|---|---|---|
| DHCP 客户端 | 停 NetworkManager，改用 dhcpcd 直接发 | 仍失败，退回 `169.254` |
| MAC 地址 | 克隆为全局唯一随机 MAC | 仍失败 |
| 广播标志 | raw socket 强制置位 broadcast flag `0x8000` | 仍失败 |
| TX 校验和卸载 | `ethtool -K eth0 tx off` | 仍失败 |

### 阶段 4｜第三方独立监听（初步收敛）
- 调试主机 UDP/67 监听：故障版本 90 秒窗口 `total=0`，一个板卡包都收不到。
- 正常版本同一监听器**收到板卡 2 个包**（`chaddr=<MAC_B>`, `TYPE=Request`）。
- 反向对照：主机发带标记的广播 → 板卡完整收到，且 `<网关IP>` 立即回 4 个 Reply，证明下行与 DHCP 服务器正常。
- 当时推断：板卡包"未真正上线"，怀疑在 MAC/PHY 层被丢弃。

### 阶段 5｜内核源码静态对比
- 下载 6.1.116 与 6.12.81 的 `drivers/net/ethernet/stmicro/stmmac/` 源码做 diff：
  - `stmmac_main.c` +814/-422；`dwmac4_dma.c` +131/-82；`dwmac4_core.c` +85/-47；`dwmac4_descs.c` +19/-13。
- 可疑点：寄存器地址查表化（`dwmac4_addrs`）、`stmmac_has_ip_ethertype()`、Split AV mode 配置。
- **认知边界**：静态 diff 只能列疑点，无法单独定根因；真正根因更可能在 Rockchip 平台驱动或 DTS，且厂商内核含大量自定义补丁。

### 阶段 6｜正常版本金标准对照
- 切到正常版本：内核 6.1.116，MAC `<MAC_B>`，拿到 `<静态IP>`。
- 连接名差异：故障版 `Wired connection 1`，正常版另一名称（用错名字会造成"零抓包"假象，已排除）。
- GMAC 两版相同点：`rk_gmac-dwmac fe010000`、RTL8211F PHY、RGMII、TX delay `0x30`/RX delay `0x10`、TX checksum on。

### 阶段 7｜切回故障版逐项对照
| 检查项 | 结果 |
|---|---|
| RGMII delay | TX `0x30` / RX `0x10`，与正常版完全一致 → 排除 |
| TX timeout / DMA reset 日志 | 无 → 排除 |
| DTB 的 GMAC 节点 | `phy-mode=rgmii`、`clock_in_out=input`、delay 值等实质相同 → 排除 |
| TX checksum 关闭（严格同步） | tcpdump 见 Discover，`tx_errors=0/tx_dropped=0`，但第三方仍 0 包 → 排除 |

### 阶段 8｜ICMPv6 主动发包，修正认知
- 板卡 ping 网关/主机 IPv6：板卡侧抓到 NS、echo request 发出，但对端零回应。
- 主机 ping 板卡 IPv6：**100% 丢包**；但板卡侧抓到——收到 10 个 NS、0.1ms 内发出 7 个 NA，`echo request=0`（对端始终没收到 NA，NDP 未完成）。
- **修正**：板卡 TX 软件层面确实在发包，但对端收不到 → 指向**单向发送故障**，而非"TX 完全失效"。

### 阶段 9｜MAC 克隆决定性实验
- 用户澄清路由器无 MAC 过滤，`<MAC_B>` 仅为静态绑定 `<静态IP>`。
- 将故障版 MAC 克隆为 `<MAC_B>`：
  - 第一轮偶发 1 个 Reply；
  - 第二轮 55 秒长窗口：**8 个 Discover / 0 Reply / 0 Offer / 0 ACK**，仍拿不到 IP，NM 报 `IP configuration could not be reserved`。
- **即使 MAC 完全正确、静态绑定存在，依然失败 → 排除 MAC 过滤/绑定因素。**

### 阶段 10｜有线口第三方最终复验
- 调试主机加装有线接入（`<本机有线IP>`），与板卡同段同二层，排除无线桥接干扰。
- 恢复板卡原 MAC `<MAC_A>` 后复验：
  - 板卡侧抓到 5 个 Discover（退避正常）；
  - 主机有线口 UDP/67 监听 60 秒窗口 **`total=0`**。
- **阳性对照**：主机从有线口自发 4 个广播，监听器收到 8 个（自发自收各两份）→ 证明监听路径完全有效，`total=0` 不是误判。
- **历史金标准**：正常版本时同一监听器曾收到板卡包。

---

## 4. 关键证据汇总

| 实验 | 结果 | 排除/指向 |
|---|---|---|
| 报文逐字节解析 | 完全合规 | 排除报文畸形 |
| 换客户端 NM / dhcpcd | 均失败 | 排除客户端实现 |
| 换 MAC（含克隆 `<MAC_B>`） | 均失败 | 排除 MAC 过滤/绑定 |
| 改 broadcast flag | 失败 | 排除单播 Offer 回不来 |
| 关 TX checksum | 失败 | 排除校验和卸载 |
| RGMII delay / DTB / timeout | 均正常一致 | 排除时序与配置差异 |
| IPv6 回程（NA 发出但对端收不到） | 100% 丢包 | 指向 TX 未上线 |
| 本机换有线口同二层监听 | `total=0`（阳性对照有效） | 排除无线桥接隔离 |
| **正常版本同一监听器** | **收到板卡包** | **唯一变量 = 内核版本** |

---

## 5. 结论

**故障根因：故障版本 `6.12.81-rk35xx-ophub` 内核的 GMAC TX（发送）路径存在回归。**

板卡发出的包在驱动层被报"发送成功"（tcpdump 可见、`udp sum ok`、`tx_errors=0/tx_dropped=0`），但**没有真正通过网卡上线**，因此对端（DHCP 服务器、同二层主机）始终收不到。这统一解释了：

- DHCP Discover 到不了服务器 → 零 Offer → 拿不到 IPv4；
- ICMPv6 的 NA/reply 到不了对端 → IPv6 ping 100% 丢包、NDP 无法完成；
- 换 MAC、换客户端、关卸载、改广播标志全部无效；
- **换回 6.1.116 版本立即正常**。

正常版本能拿到 `<静态IP>`，是因为其 TX 路径正常、Discover 能到路由器，且 `<MAC_B>` 在路由器上有静态绑定。故障版即便克隆成 `<MAC_B>`，包也到不了路由器，静态绑定无从生效。

此次排查中"路由器 MAC 过滤"和"包在 PHY 层丢弃"两个中间假设均已被后续实验推翻，以本节结论为准。

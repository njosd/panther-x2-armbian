# 项目 A：干净基线与网络组件隔离决策

- 日期：2026-11-22
- 项目：Panther X2 项目 A（最小系统与基础网络验证）
- 决策等级：**强制架构原则 / B1 准入条件**
- 状态：决策已写入权威路线；具体组件清单和隔离产物尚待审计、构建与验证

## 1. 决策背景与项目初衷

项目 A 的目标不是一步得到一个完整的 Linux 6.18 系统，而是建立一个干净、可重复、可审计的实验环境，从最小启动能力开始逐级搭建。每次只增加一个组件或一个不可再拆分的最小依赖闭包，通过前后对照判断该组件是否改变系统行为。

如果将项目 B 中曾经出现问题、但根因尚未解决的 GMAC 或其他网络相关组件直接带入 B1，那么 B1 一旦出现类似网络故障，就会再次面对多个未知变量叠加、无法归因的局面。这背离项目 A 的初衷。

因此，**B1 必须先隔离 GMAC，以及所有其他未经审查、可能影响网络启动或网络收发结果的组件。** 干净基线是项目 A 的硬性前置条件，不是可选优化。

## 2. 项目 A 与项目 B 的边界

- 项目 B 的网卡故障根因调查、GMAC/MDIO/PHY 专项根因排障继续作为独立历史专题；本决策不恢复这些根因调查。
- 项目 A 必须继承项目 B 的历史报告、源码审计、日志和实验结果，将已知风险作为隔离设计输入；不得重复已有且证据充分的专项实验。
- 项目 A 的隔离和逐项引入是为了控制变量、验证最小系统和基础网络能力，不是继续追查项目 B 的故障根因。
- 若某组件重新引入后出现异常，项目 A 记录该组件引入前后的可观察差异、日志和停止点；不自动扩展为专项根因调查。

## 3. B1 初始干净基线的边界

初始基线只包含启动和最小 RAM 用户空间所必需的组件：

- 固定的 ARM64 Kernel 与 Panther X2 专用 DTB；
- 与启动方式兼容的最小 initramfs；
- /init、静态 BusyBox 和 UART 交互 shell；
- 必要的串口、CPU/内存、设备树、RAM 文件系统支持；
- 必要的 TF/SD 读取与 MMC/eMMC 识别能力；
- 经审查确认不会引入网络变量的其他启动必需依赖。

初始基线不得默认包含或启用：

- GMAC/STMMAC/DWMAC 及其他 MAC/以太网控制器驱动；
- MDIO、PHY、PCS 等网络链路专用驱动；
- 其他未经审查的有线/无线网络设备驱动；
- 网络协议栈及其非启动必需功能；
- ip、ARP/ICMP、TCP/UDP 测试工具等网络用户空间工具；
- DHCP、DNS、SSH、NetworkManager、systemd、udev 等服务或管理框架。

上述项目不是永久禁止，而是在干净基线通过前不得混入。后续必须按单变量计划逐项加入。

## 4. 必须审查的网络影响面

不能只搜索 GMAC 名称，也不能把所有名字含 network 的配置简单关闭。构建前需建立依赖审计清单，至少覆盖：

1. **设备与总线驱动**：MAC/以太网控制器、GMAC/STMMAC/DWMAC、MDIO、PHY、PCS，以及可能存在的其他网络设备驱动。
2. **网络内核能力**：网络协议族、packet/inet、IPv4/IPv6、ARP、ICMP、socket、netfilter 等与当前目标相关的配置；确认哪些属于干净基线必须排除，哪些只在后续阶段引入。
3. **设备树与硬件依赖**：MAC/MDIO/PHY 节点、pinctrl、clock、reset、regulator、DMA、中断、供电及相关引用关系。
4. **用户空间与服务**：网络工具、后台服务、自动配置程序、udev/NetworkManager 等可能自动改变接口状态或网络配置的组件。
5. **隐含依赖与共享基础设施**：识别同时服务 UART、MMC/eMMC、PMIC 或其他启动必需设备的共享资源。不得为隔离网络而盲目关闭共享 clock/reset/pinctrl/regulator/DMA 等基础设施；必须精确到设备节点和依赖关系。

每项标注：组件名称、Kconfig/驱动/DT 节点、依赖项、是否编入内核、是否作为模块、是否会 probe、初始基线处理方式、后续引入顺序和验证证据。

## 5. 两层隔离必须分别有证据

### 5.1 Kernel 构建层

- 干净基线使用独立配置，不直接沿用 Ophub 完整内核配置。
- 对相关 Kconfig 及依赖进行审计，确认网络专用驱动没有以 built-in 或 module 形式进入基线。
- 最终 .config、构建日志、模块清单和必要的二进制/符号检查必须一致。
- CONFIG_STMMAC_ETH=y、CONFIG_DWMAC_ROCKCHIP=y 等状态不能出现在声称已完成驱动代码隔离的基线中。
- 仅有 DTB 节点 disabled 不代表驱动代码已从 Kernel 中移除。

### 5.2 DTB 设备层

- 对 Panther X2 原始 DTB 做只读结构审查，定位网络设备节点及其引用依赖。
- 派生独立测试 DTB，禁用或排除初始基线不应参与 probe 的网络设备节点。
- 反编译后的 DTS/结构检查、节点状态和依赖关系必须留档。
- 不得修改或覆盖原始 DTB；每个派生版本记录源文件哈希、修改差异和最终哈希。

Kernel 代码隔离与 DTB 设备隔离是两个不同条件，必须同时满足。不得把其中一项冒充另一项。

## 6. 逐项引入顺序与试验纪律

干净基线启动通过后，按依赖关系拆分并逐项引入。具体顺序由审计结果决定，不能在未完成依赖分析前预设所有驱动都可独立拆分。原则上按以下层次组织：

1. 网络内核基础能力（仅加入当前下一项试验所需的最小配置）；
2. 目标 MAC/GMAC 驱动及其最小必需依赖；
3. MDIO/PHY/PCS 等链路组件，按实际依赖拆分；
4. 其他可能影响网络行为的硬件或软件组件；
5. ip 等只读接口检查工具；
6. 接口启用、地址、路由、ARP、ICMP；
7. TCP 与 UDP 分开验证；
8. 最后才按明确需求评估 DHCP、DNS、SSH 等复杂服务。

若某驱动必须与一个不可再拆分的依赖闭包一起引入，该闭包作为本轮唯一变量，必须完整记录。每轮固定其他全部输入；保存构建配置差异、Kernel/DTB/initramfs 哈希、启动日志、probe 状态和测试结果。

某组件加入后若出现异常：
- 立即停止，不加入下一组件；
- 保存该轮构建产物、配置差异、UART/kernel 日志和设备状态；
- 回退到最近已验证基线；
- 只记录“该组件/依赖闭包加入后首次出现变化”的证据，不未经专项授权就推断其内部根因。

## 7. B1 准入门槛

在 B1 进入实际启动测试前，必须完成：

- 干净基线组件白名单与排除清单；
- Kernel 网络相关 Kconfig/依赖审计；
- GMAC/STMMAC/DWMAC 等驱动不进入基线的最终配置证据；
- Panther X2 DTB 网络设备节点隔离证据；
- 共享硬件依赖检查，确认 UART、MMC/eMMC、PMIC 等启动必需功能未被误伤；
- Kernel、DTB、initramfs 的来源、版本和 SHA-256 锁定；
- 构建和静态检查通过；
- 原始 Ophub 6.18.64 等完整包仅保留为对照/素材，不得直接冒充干净基线。

任何一项缺失，B1 不放行。eMMC pre-Linux 写入安全门和用户逐次授权仍是独立的必要条件；本决策不授权写 TF、启动设备或修改 eMMC。

## 8. 当前状态

已确定：
- B1 必须先隔离 GMAC 及其他可能影响网络行为的未经审查组件；
- 初始基线不预置网络工具或复杂网络服务；
- 基线通过后按单变量方式逐项引入；
- 项目 A 不承担项目 B 的故障根因调查。

尚未完成：
- 对当前候选 6.18.y 内核配置进行完整网络依赖审计；
- 对 Panther X2 原始 DTB 完成网络设备节点及共享依赖审查；
- 生成并审计真正的干净 Kernel/DTB；
- 运行构建、静态验证及目标硬件启动测试。

本报告记录的是架构决策，不代表 GMAC 已经被实际移除，也不代表已经产生可启动的干净镜像。

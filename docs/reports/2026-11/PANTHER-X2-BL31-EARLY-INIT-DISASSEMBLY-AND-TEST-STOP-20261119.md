# Panther X2：BL31 早期初始化反汇编审计、DDR 频率边界与本轮测试收口（2026-11-19）

- 范围：`0x55700–0x557a0`、`0x5c238–0x5c280`、`0x5c400–0x5c7d4` 及相关 BL 指令交叉引用
- 性质：静态反汇编分析；未修改设备、镜像、驱动或配置

用户依次提供了以下反汇编窗口：

这些是同一 ELF、同一基址参数下的静态代码窗口，不是多轮不同固件实测。

## 2. 调用关系：已能确定的结构

### 2.1 BL31 中的调用点

反汇编交叉引用显示，BL31 内存在多个调用到 `0x5c...` 区域的分支，包括：

- `0x55728 -> 0x5c238`
- `0x5c24c -> 0x5cf50`
- `0x5d8c4 -> 0x5cf50`
- 其他被列出的调用点：`0x55768 -> 0x5cb64`、`0x55780 -> 0x5c9d0`、`0x55784 -> 0x5cb44`、`0x5d07c -> 0x5ce6c`、`0x5d0a8/0x5d0b0/0x5d0b8/0x5d0c0/0x5d0c8 -> 0x5cfc8` 等。

`0x55728` 所在的路径在调用 `0x5c238` 后继续检查状态字段，并返回上层；`0x55768` 一带则是另一组独立调用路径。仅凭这些调用点，不能把所有 `0x5c...` 子程序视为同一初始化函数。

### 2.2 `0x5c238` 的可见执行顺序

在 `0x5c238`：

1. 通过阶段标记函数 `0x559d8` 记录数值 0x41；
2. 调用 `0x5cf50`；
3. 记录 0x42；
4. 调用 `0x5d330`；
5. 记录 0x43；
6. 随后从 `0x78000` 附近的数据区取参数，并进入后续配置/复制代码。

这里的 0x41/0x42/0x43 是传给 `0x559d8` 的数值。尚未将该函数及其参数与可读日志字符串、具体硬件模块或公开 TF-A 源码符号建立可靠映射，因此不将它们命名为 GMAC、DDR、时钟或其他具体阶段。

## 3. `0x5c400–0x5c7d4` 的内存操作特征

反汇编显示该区域包含多组从内存数据区读取 32-bit word、再写入固定地址区的操作：

- `0x5c424–0x5c464`：从 `0x79000` 附近的数据结构读取多个 word，写入以 `0xfdca8000` 为基址的地址区。
- `0x5c49c–0x5c4dc`：另一组参数写入 `0xfdca0000` 附近的地址区。
- `0x5c4e0–0x5c518`：将若干 word 写入 `0xfdca8040` 附近的地址区，并有一个偏移写入。
- `0x5c520–0x5c534`：以 4 字节步进复制数据，循环边界为 `0x90` 字节，目标基址由前序代码设为 `0xfdd20300`。
- `0x5c538`：调用 `0x5d3b0`。
- `0x5c53c–0x5c5b8`：从 `0x78000` 附近的数据结构读取字段，写入 `0xfdd200c0`、`0xfdd200d0` 等位置；其中部分字段经过 `orr #0xffff0000`，另一些字段直接写入。
- `0x5c5c0–0x5c608`：一个以 4 字节递增的复制/筛选循环。代码对输入偏移 `0x130`、`0x1d4` 及 `0x214`、运行时寄存器 `w6`、`0x254` 等边界进行比较，并对部分区间跳过写入；其余 word 从源表读取后经 `orr #0xffff0000` 写入目标地址。
- `0x5c60c–0x5c6c4`：多组循环从 `x0` 指向的源数据读取 word，并写入 `0xfdd2xxxx` 目标区；循环边界分别包括 `0x300–0x390`、`0x400–0x478`、`0x480–0x550`。
- `0x5c6c8–0x5c764`：从 `0x79000` 和 `0x78000` 附近的数据结构读取字段，写入 `0xfdd1xxxx` 目标地址，并调用 `0x5d43c`。
- `0x5c768` 以后继续调用若干子程序，并通过 `0x559d8` 传递 0x44、0x45、0x46、0x47 等阶段值。

### 证据边界

以上可以确认这是有结构的参数/表项搬运与固定地址写入流程，不是简单的字符串输出代码。但当前反汇编没有符号表、寄存器地址定义、对应 C 源码或芯片寄存器映射，因而：

- 尚不能确认 `0xfdca....`、`0xfdd1....`、`0xfdd2....` 各地址分别属于哪个 Rockchip 子系统；
- 尚不能确认 `orr #0xffff0000` 是掩码/标志位、保留位设置还是该固件内部的特定数据编码；
- 尚不能确认这些表项是否包含 GMAC、时钟、PMU、QoS 或其他设备配置；
- 不得仅凭地址外观把该代码段直接命名为 GMAC 初始化或 DDR 初始化。

后续如有必要，最有效的静态工作是先识别 ELF 的 TF-A 版本/平台构建来源与链接布局，再把这些固定地址映射到 RK3566 TRM/头文件或同版本 TF-A 源码；不应继续无目标地扩展反汇编窗口。

## 4. DDR 降频问题：因果边界已经收窄

2026-11-19 实机启动日志已确认：

- 本轮执行的是 JP idbloader 中的 SPL / DDR 初始化代码；
- DDR banner：`DDR Version V1.10 20210810`；
- LPDDR4，识别 4096MB，CS0/CS1；
- 训练过程记录 324、528、780、1056MHz，最终 1056MHz；
- 对照旧 SPL / DDR V1.13（2022-02-18），旧日志最终频率为 1560MHz。

因此，当前观察到的 1056MHz 与 1560MHz 差异，首先属于 SPL 所携带的 DDR 初始化实现/参数差异。DDR training 和最终频率选择发生在 SPL 阶段，早于 BL31 的运行。

**重要结论：本报告反汇编的 BL31 代码位于 SPL/DDR 初始化之后，不能作为本次 SPL 最终只训练到 1056MHz 的直接原因。** 除非另有证据证明后续固件再次改变 DDR 时钟，否则不应把 BL31 这段内存写入代码与 SPL DDR training 结果混为一谈。

本轮只确认两版启动代码的实际频率差异，没有进行内存带宽、压力、温度或长期稳定性测试；不能据此判定 1056MHz 是故障、保守策略或性能缺陷。

## 5. IPv4 DHCP 故障：当前证据与已排除方向

结合 2026-11-19 JP idbloader 实机结果：

- JP SPL / DDR V1.10 已实际执行，系统成功启动 Linux 6.12.81；
- U-Boot proper 枚举 GMAC1：`ethernet@fe010000`；
- Linux RTL8211F PHY 识别成功，RGMII 配置完成，链路为 1000Mbps Full；
- Linux 运行时 MAC 仍为 E6 前缀；
- IPv4 DHCP 未取得租约，IPv4 路由表为空；
- IPv6 已取得全球单播地址；
- 本轮没有 Panther 与 hEX 同步抓包，没有本轮 DHCP Discover 的逐包线侧证据。

由此可以确认：**仅将 eMMC LBA64 的 SPL/idbloader 替换为 JP 版本，不能使 IPv4 DHCP 故障自动消失。** 这降低了“旧 SPL/DDR V1.13 本身就是 DHCP 故障唯一原因”的可能性，但并不证明 U-Boot/启动链对 GMAC 完全没有影响。

MAC 来源已经通过此前工作形成结论，后续不再把“重新查 MAC 来源”列为主线，也不重复 MAC 地址来源审计。当前需要解释的是：在 PHY/链路正常、运行时 E6 前缀保持、Linux 发起 DHCP 但未取得租约的条件下，Discover 是否真正越过 PHY 并到达 hEX。

## 6. 本轮测试收口与 eMMC 恢复状态

本轮 JP idbloader 写入实验的目标是验证 SPL/DDR V1.10 是否能在 Panther X2 上完整启动，并观察是否改变 IPv4 故障。

实验结果已足以回答这个问题：

1. JP idbloader 可在 Panther X2 上完成 DDR 初始化并启动后续 TF 启动链；
2. 系统可以启动 Linux 6.12.81；
3. IPv4 DHCP 故障仍存在；
4. DDR 最终频率为 1056MHz，低于原 SPL/DDR V1.13 记录的 1560MHz；
5. 替换 SPL 没有解决当前网络故障。

用户随后确认原始 eMMC 首 32MiB 备份存在，文件：
`/Users/osd/panther-recovery/emmc-first32m.bin`
大小 33,554,432 bytes，SHA-256：
`bf99a3b47aa738a7ea68a885ccd5a45119cd242e16d5595457e1beb46c34839b`

恢复过程中，eMMC 原始 `idbloader.img` 内容（文件本体 596 sectors + 8 sectors 零填充）哈希为：
`336acab5b842605b044f0e15851751cbf9eeef45dfd568af2b025d748f36ba07`

恢复后从 eMMC LBA64–667 回读的 604 sectors 哈希同为：
`336acab5b842605b044f0e15851751cbf9eeef45dfd568af2b025d748f36ba07`

同时，原始 eMMC `idbloader.img` 文件哈希为：
`990afd3e1a96094a1b6ef0b32ea55cb9cb2d6de53bd7e368d6c77fea4eddd91e`

因此，**原版 eMMC SPL 恢复已有读回哈希证据；本轮 JP SPL 替换实验可以收口，不需要继续占用正常启动环境。** 后续若需要再次实验，应先确认当前设备实际启动 SPL banner 与 DDR 版本，不重复写入或重跑已完成的验证。

## 7. 后续工作量与优先级

### P0：保留已恢复的稳定基线

- 不再对 eMMC 启动区进行无目标写入；
- 保留 6.1.116 正常运行基线及原始备份；
- 后续启动先用 UART 确认实际 SPL/DDR 身份，避免把 TF 上的文件误认为本次已执行。

### P1：若继续定位 IPv4 DHCP，只做一次有区分度的边界测试

唯一优先项是同一 DHCP Discover 的两端关联：

- Panther 侧被动记录 Discover 的时间、报文标识和 Ethernet source MAC；
- 同一时间窗口在 hEX 入口观察是否收到同一报文；
- 不把 Linux outgoing packet capture 单独当作 PHY 线侧发送成功；
- 不重复 PHY ID、链路、RGMII delay、基础时钟、MAC 来源、普通 ping 或泛化 DHCP 测试；
- 不先改 MAC、内核、设备树、网络配置或路由器配置。

若没有自然产生的 Discover，是否允许受控触发应另行明确授权。

### P2：DDR 频率差异只做静态来源核对

若用户仍希望解释 1056MHz 与 1560MHz 的差异，先比较两套 SPL 中 DDR 参数/训练配置及其来源。没有必要立即进行内存压力或性能测试；更不能为追求 1560MHz 直接修改 DDR 参数。

### 暂停项

在没有新证据前，暂停无目标扩展 BL31 反汇编、重复完整启动测试、重复 MAC 来源追踪及重复 GMAC 基础审计。
